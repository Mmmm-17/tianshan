## 10月1日：项目定盘与第一天点灯

**今日做了什么：国庆首日，队里开了个短会，把整辆小车的技术路线定下。今年 CRTC 是资源争夺赛，底盘我们择了四轮麦克纳姆轮——理由极简：场地障碍密布、道具散落，能横行比只会转弯金贵得多。会后背下任务：主控用 STM32F103C8T6（Blue Pill），我负责把程序从零写到能跑。**
会后头一桩，是把工具链装妥。CubeMX 建工程、Keil 编译、ST-LINK 烧录，这趟流程国庆前只听过名头，今日方是头回自个儿走完。下午写就人生第一个嵌入式程序：令 PC13 上那颗板载 LED 闪烁。
    ```cHAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET);HAL_Delay(500);HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);HAL_Delay(500);```
**收获：略知"推挽输出"大概何意——引脚既能主动吐高电平，亦能主动拉低。至于开漏输出、复用推挽之流，当时全然辨不清，是后来学长讲了一回才略生概念。`HAL_Delay()` 仰赖 HAL 库的 SysTick 计数、故须先 `HAL_Init()`，此条乃 AI 提醒，我自己并未看出因果。**
**问题：首回烧录失败，Keil 报"no target connected"。查了半晌，竟是杜邦线把 SWDIO 与 SWCLK 插反了。调正之后，一次即成。**
**想到的：灯亮与否，本说明不了什么，却证了一桩事——我的代码真能钻进芯片，芯片也真按我说的办。这重反馈对整个项目至关紧要，往后每回改代码，我都借它确认链路是通的。**

## 10月2日：按键输入与"下降沿"的思路

**今日做了什么：由"输出"跨入"输入"。将 PA0 配为上拉输入，接一枚按键，按一下令 LED 切换状态。**
第一版代码写得极直白：
    ```cif (HAL_GPIO_ReadPin(GPIOA, GPIO_PIN_0) == GPIO_PIN_RESET) {HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);}```
结果灯疯狂闪烁——因程序一秒跑几十万次，手指按下的那几十毫秒里，判断被执行了上万回，灯便被翻转了上万回。
**改进：引入"边沿检测"之念——不判"此刻是否按下"，而判"上一刻松开、这一刻按下"。**
    ```cstatic uint8_t last = 1;uint8_t now = HAL_GPIO_ReadPin(GPIOA, GPIO_PIN_0);if (last == 1 && now == 0) {   // 1→0，下降沿HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);}last = now;```
**收获：这"看变化、不看状态"的写法，状态本身不带信息，变化才带，后来在 PS2 手柄的按键处理与电机正反转切换上，皆用了同一套。**
**问题：上拉输入为何必不可缺？查了资料方悟：若引脚悬空，读到的电平是随机的，盖引脚如一根天线，会拾取周遭干扰。上拉即把引脚"默认拉至高电平"，按键按下时将其短路到地，如此方有确定的两态。此疑是我揣着面包板去问学长，他两分钟画张图便讲透——这种"当场有人能问"的资源，比任何网课都值钱，往后我基本养成了有疑当日即问掉的习惯。**

## 10月3日：PWM 呼吸灯

**今日做了什么：今日首度触碰定时器。目标是以 TIM2 的 PWM 输出，令 LED 由暗及亮、复归于暗，做出"呼吸"之效。**
配置：72MHz 时钟，PSC=71，ARR=999，得到 1kHz 的 PWM 频率。随后在主循环里从 0 缓缓加至 1000，再自 1000 缓缓减回 0。
    ```cfor (int i = 0; i <= 1000; i += 10) {__HAL_TIM_SET_COMPARE(&htim2, TIM_CHANNEL_1, i);HAL_Delay(10);}```
**收获：终将 PWM 想通透。占空比决定的，是"平均电压"，而非"开关频率"。人眼难辨 1kHz 的闪烁，唯见亮度，故占空比 30% 看上去便是 30% 的亮度。这层理解直接迁至电机调速——电机亦循"平均电压决定转速"之理。**
**问题：起初呼吸灯是"跳"的，而非"呼吸"。缘由是我把步长设成 100，仅得十档。改成 10 之后，方有平滑过渡。这令我悟得：分辨率是效果的一部分，粗粒度采样看上去便卡顿。**
**想到的：PWM 在两端全然不相干之处，用的竟是同一套逻辑——LED 的亮度、电机的转速。那几日培训听过的"占空比"三字，至此刻才算落进手里，此前它不过是个词。**

## 10月4日：USB 虚拟串口——给调试装上眼睛

**今日做了什么：前三天调程序，全凭"灯闪几下"来判，效率极低。今日把 USB CDC 配上，令板子一插电脑便现一个虚拟串口，可直接往上打印。**
在 CubeMX 里勾选 USB 的 Device (FS) 模式，Middleware 中选 CDC。生成代码后，重写 `CDC_Transmit_FS()` 的封装：
    ```cvoid MyPrintf(const char *fmt, ...){char buf[128];va_list ap;va_start(ap, fmt);vsnprintf(buf, sizeof(buf), fmt, ap);va_end(ap);CDC_Transmit_FS((uint8_t*)buf, strlen(buf));}```
**收获：这个 `MyPrintf` 是我照着 AI 给的模板抄的，`va_list`、`va_start`、`vsnprintf` 这几样，当时全然不明其所以，只知"这么写便能如 printf 般打印"。直至后来查变量用了几十回，才约略明白 va_list 是"把不定个数的参数打包"。**
**问题：串口助手收不到数据，查了良久。末了发现是 `CDC_Transmit_FS()` 返回 `USBD_BUSY` 时被径直丢弃——USB 发送是异步的，上一包未发完，下一包便遭拒。加了个重试循环后解决。**
**想到的：这是整个项目里性价比最高的一桩事。有了串口，我可将任意变量的值打出，"看不见"之物顿成"看得见"。往后所有的调试，皆立基于此。**

## 10月5日：理解 DRV8833——从 3 线到 2 线

**今日做了什么：程序要"动"，便得碰电机。今日始啃 DRV8833。**
翻资料时踩了个坑：网上大多教程讲的是"3 线方案"——IN1 控方向、IN2 控方向、外加一枚独立 EN/PWM 脚控速度。我循此思路画了接线图，拿去与硬件那边对，却被告知"DRV8833 没有独立的使能脚"。
回头将芯片手册读了第二遍，方悟 DRV8833 每路仅余两个输入脚（AIN1/AIN2）。其内为双 H 桥，两脚组合共成四种状态：

| IN1（方向脚） | IN2（PWM） | 电机状态 |
| --- | --- | --- |
| 1 | PWM | 正转，速度由占空比决定 |
| 0 | PWM | 反转 |
| 0 | 0 | 滑行停（高阻） |
| 1 | 100% | 刹车锁死 |

**换言之，速度并非靠单独一枚 PWM 脚驾驭，而是在两只方向脚之一上打 PWM。此即所谓"2 线方案"。**
**收获：吃透了 H 桥的真值表逻辑，亦理解了"方向 + 速度分离控制"之思——一只脚定方向，另一只脚定快慢。**
**问题：这四种状态里，`0 0` 是滑行停、`1 1` 是刹车锁死，二者看似皆为"停"，电机行为却截然不同。当时我未加在意，只道"反正都是停"。这念想，在四日后引出一桩令我卡了整整一日的问题。**
**想到了：芯片手册务必读原始文档，不可只看二手教程。二手教程会把芯片"简化"成其常见模样，而遭简化的那截，往往正是坑。**

## 10月6日：第一次让轮子转起来

**今日做了什么：将单个电机的驱动代码写通。初始化两个 GPIO 为输出，一个给高电平当方向，另一个借定时器输出 PWM 当速度。这段代码，我先是管 AI 要了个框架，再比照培训笔记改——AI 给的版本用的是 3 线思路，与我们的实际接线对不上，改了两遍才跑起来。**
    ```cstatic void MotorA_Set(int16_t speed)   // -1000 ~ 1000{if (speed >= 0) {HAL_GPIO_WritePin(GPIOB, AIN1, GPIO_PIN_SET);__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, speed);} else {HAL_GPIO_WritePin(GPIOB, AIN1, GPIO_PIN_RESET);__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, -speed);}}```
以带符号的 `int16_t` 表征速度与方向，这一设计后来省却许多麻烦——上层只管传一个带正负号的数，正负号背后的方向逻辑，尽数消化于该函数之内。
**收获：头一回令东西真正"动"起来。轮子转起的那一瞬，声响颇噪，心情却极好。**
**问题：发觉低速时电机不转，还"嗡嗡"作响。查后方知是启动死区——占空比低于某值（TT 马达约 15% 左右），力矩不足以克服静摩擦。此问题日后须以"起步给个大值、稳定后再降"之法绕过。**

## 10月7日：麦克纳姆轮的方向表

**今日做了什么：四轮皆能独转，接下来便是令它们协同。麦克纳姆轮的轮缘密布 45° 斜向滚子，四轮组合，竟能做出普通车轮难及的横移与原地旋转。**
先定布局：A（左前）、B（右前）、C（左后）、D（右后），标准的 2×2 十字布局。
继而绘方向表——此乃全向移动的魂魄：

| 动作 | 左前 A | 右前 B | 左后 C | 右后 D |
| --- | --- | --- | --- | --- |
| 前进 | 正 | 正 | 正 | 正 |
| 后退 | 反 | 反 | 反 | 反 |
| 左平移 | 反 | 正 | 正 | 反 |
| 右平移 | 正 | 反 | 反 | 正 |
| 左转 | 反 | 正 | 反 | 正 |
| 右转 | 正 | 反 | 正 | 反 |
| 停止 | 停 | 停 | 停 | 停 |

绘毕自验算一遍：前进是四轮皆正，好懂；左平移时左侧两轮须反着转、右侧两轮正着转，如此斜向滚子合成的力才朝左。以"矢量合成"之思在纸上勾画受力方向，确然对得上。
**收获：这是头一回真正参透"全向移动"的原理。它并非魔法，而是四个 45° 滚子的力，在某一方向上相消、在另一方向上相叠。**
**问题：表画得颇顺，落到代码上却一团乱麻——四轮、两向、七种动作，写出来竟是二十几个 if。**

## 10月8日：反装轮与逻辑层抽象

**今日做了什么：昨日那"二十几个 if"写得委实太丑，今日重构了一番。**
**重构的核心发现是：B、D 两枚电机是反着装的。因车体左右对称，右侧电机须反向固定，方能让轮子朝外。这引出一桩结果——代码里写"正转"（引脚拉高），B、D 实际转的方向，恰与 A、C 相反。**
初版我在每个 if 里单独处理，写着写着便乱。后来想通透：应将这"硬件差异"收敛到一处。
    ```c
    #define A_DIR_FWD  1
    #define B_DIR_FWD  0    // 反装，正转电平相反
    #define C_DIR_FWD  1
    #define D_DIR_FWD  0
    static void Wheel_Set(uint8_t id, int16_t speed)  // speed>0 表示"逻辑正转"{GPIO_TypeDef *port = wheel_port[id];uint16_t fwd_pin   = wheel_fwd_pin[id];uint16_t pwm_ch    = wheel_pwm_ch[id];uint8_t  fwd_level = wheel_fwd_level[id];
    if (speed >= 0) HAL_GPIO_WritePin(port, fwd_pin, fwd_level ? GPIO_PIN_SET : GPIO_PIN_RESET);else            HAL_GPIO_WritePin(port, fwd_pin, fwd_level ? GPIO_PIN_RESET : GPIO_PIN_SET);__HAL_TIM_SET_COMPARE(&htim3, pwm_ch, speed >= 0 ? speed : -speed);}```
**收获：这是项目里最重要的一次代码设计。逻辑层（"这个轮子该正转"）与硬件层（"这个引脚该输出什么电平"）被彻底劈开。上层填方向表时，只需写"正/反"，全然不必操心哪几枚轮子反装。**
**问题：宏定义与数组索引混用，起初将数组下标与物理编号搞混，A 与 B 的 PWM 通道接反，车跑起来画圈。靠串口打印每个轮子的速度值，方才定位。**

## 10月9日：麦轮跑起来了，但走不直

**今日做了什么：将方向表接进代码，以按键切换动作。前进、后退、左右平移、左右旋转，七种动作悉数能演示。**
**问题：车行不直，明显朝一侧偏。起初疑为电机差异，量了四轮空载转速，确有些许差别（最快与最慢约差 8%）。然调过代码里的补偿系数，依旧偏。**
**再查，方现是轮子装得不够方正——底盘板上四枚马达座是打印件，加工误差令四轮轴线不再平行。此乃机械之过，非代码之责。**
**收获：头一回真切体认到"软硬件是耦合的"。代码写得再对，硬件若偏差，结果便是错。这令我日后养成一习：出问题先分清是"逻辑错"还是"物理错"。**
**问题（遗留）：走直线的补偿系数，眼下是拍脑袋定的 1.00 / 1.05 / 0.98 / 1.02，并无依据。此节后续须靠编码器方能真正解决。**

## 10月10日：上电乱转——一个卡了整天的 bug

**今日做了什么：今日撞上整个项目最难的一桩问题。**
**现象：程序烧毕，每次上电刹那，B、D 两轮会自顾满速转起，A、C 不动。按一下按键，四轮方复常。**
**排查过程（此乃今日最值钱的部分）：**
**① 先疑"切换瞬态"——排除。因现象是持续的，而非闪一下。**
**② 查软件层：PWM 极性对否？定时器通道配错否？GPIO 复用冲突否？——逐项排去，尽皆正常。**
**③ 做互换实验：将 B 的驱动模块与 A 的模块物理对调，结果仍是 B 那个位置转。这便证了：问题随"引脚与代码"走，非模块损坏。此步将范围收窄大半。**
**④ 逐行审视初始化代码——发觉上电时我调用了一次"停止"函数，而我的"停止"实现是刹车停：四枚方向脚全拉高、PWM 给满。**
**看到此处，豁然贯通。对 A、C 而言，方向脚高 + PWM 满 = 刹车锁死，轮不动，契合预期。然对反装的 B、D 来说，方向脚高恰是"反转"电平，PWM 又给满——它们非是刹车，而是满速反转！**
**根因：`刹车停`此一实现，与`反装轮`这宗硬件特性生了冲突。两件单看皆对的事，凑到一处便错。**
**解决：将停止方式由"刹车停"改为"滑行停"——方向脚拉低、PWM 清零。同时于初始化里显式将全部方向脚拉低、占空比清零，绝不依赖任何默认态。**
**收获：习得逐层排查、控制变量、互换实验这套法门。尤以"互换实验"为甚——它借一次物理动作，便把"软件问题"与"硬件问题"劈开，远胜盯着代码枯看一小时。**

## 10月11日：PS2 手柄——手动模拟 SPI

**今日做了什么：按键控制只做得出"固定动作"，要达成"连续遥控"，便须上手柄。今日始啃 PS2。**
**PS2 接收器与单片机间是类 SPI 的协议，四根线：DAT（数据）、CMD（命令）、CLK（时钟）、ATT（片选，有的板子标 CS）。与标准 SPI 不同处在于，PS2 要求手动控制时序——拉低 ATT，随后在 CLK 的每个下降沿收发一位，总共 9 个字节。**
    ```cstatic void PS2_Transfer(uint8_t *cmd, uint8_t *buf, uint8_t len){PS2_CS_LOW();for (uint8_t i = 0; i < len; i++) {buf[i] = SPI_SwapByte(cmd[i]);   // 发一个字节，收一个字节}PS2_CS_HIGH();}```
**收获：终得领悟 SPI 的"全双工"何意——发送与接收同时发生，每发一位便同时收一位。从前看资料说"全双工"，一直以为是"能同时发、收两样不同的东西"，今日方明，是同一条时钟节拍上，一根线出、一根线进。**
**问题：读回的全是 `0xFF`。查了半日，是初始化序列少了一段——手柄须先收到一串"进入模拟模式"的命令（`0x01 0x43 0x00 0x01 0x00`），其后回包里方有摇杆数据，否则一直返空包。**
**想到了：协议这东西，"能收到数据"与"能收到有用的数据"是两截截然不同的阶段。前者只须线接对，后者须将每一帧的格式吃透。**

## 10月12日：从"按键查表"到"连续控制"

**今日做了什么：手柄已能读数据，今日任务，是把摇杆的模拟量化作四轮的速度。**
先厘清摇杆输出：每轴 0~255，中值约 128。继而做三步处理：
**① 去中心：`axis = raw - 128`，化为 -128~127；**
**② 死区：绝对值小于 8 的直接归零，免得手松时抖动；**
**③ 归一化：除以 128，变为 -1.0 ~ 1.0 的浮点分量。**
随后套用麦轮运动学公式，将 `vx`（左右）、`vy`（前后）、`w`（旋转）三分量合成为四轮速度：

| 轮子 | 速度公式 |
| --- | --- |
| 左前 A | vy + vx + w |
| 右前 B | vy − vx − w |
| 左后 C | vy − vx + w |
| 右后 D | vy + vx − w |

**收获：这是整个项目里最重要的一回认知转折。前此所有工夫皆是"查表"——前进便四轮正转，左移便两正两反。而公式化之后，摇杆推一半，车便走一半速；摇杆斜推，车便斜行。由"离散的动作"蜕为"连续的自由度"，这才是麦轮的真价。**
**问题：合成之后须归一化，否则斜推时，某轮速度会越过 1000（PWM 上限），致轮"削顶"，车行方向便歪。做法是先觅四速度里绝对值最大者，若逾 1，便整体按比例缩放。**
**想到的：方向表并未遭弃——它实是这公式在极端输入下的特例。验证之法：将 `vx=-1, vy=0, w=0` 代进公式，算来恰是"反 正 正 反"，与 10 月 7 号所绘表格完全一致。那一刻，颇爽。**

## 10月13日：串口调试与参数标定

**今日做了什么：摇杆控车已能跑，手感却极怪——轻推一点便疾走，推到半程却没了差别。今日主攻参数标定。**
将 `vx、vy、w` 三分量实时打往串口，一边推摇杆一边盯着数值。撞见两个问题：
**① 摇杆实际行程不对称：向上推能到 250，向下只到 20，中心值也非精确的 128，而是 122。故我先前按 ±128 归一化是错的，实际应按 `(raw - center) / (max - center)` 分别计上下两向的比例。**
**② 死区设得过大：±8 在数值上乃 8/128 ≈ 6%，然实际推杆时这区间占了可见行程的相当篇幅，教人"推了没反应"。**
调整后：记下每轴的实际中心值与上下极限，做分段线性映射；死区缩至 ±4，并在死区边缘添一小段平滑过渡，免得"跳一下"。
**收获：一切"手感"问题，本质上皆是数值映射问题。把映射关系画出，症结一目了然。串口打印在此处的作用无可替代——缺了它，我只能瞎猜。**
**问题：不同手柄的摇杆参数相异，我这标定値换一只手柄便失准。眼下先在代码里写死，注释标明"此参数只对应 1 号手柄"。**

## 10月14日：代码重构与 CubeMX 的边界

**今日做了什么：代码已写到一个 `main.c` 四百多行的地步，改一处要翻半日。今日做了次重构。**
拆作数份文件：`motor.c/h` 管电机、`mecanum.c/h` 管运动学、`ps2.c/h` 管手柄、`debug.c/h` 管串口打印。`main.c` 里仅余初始化调用与主循环。
**踩坑一：拆文件时图省事，直接将 `.c` 文件 `#include` 进 `main.c`。能编译、能跑，却属反模式——它令所有变量皆成"同一编译单元里的全局变量"，重名便直接冲突，且摧毁了模块化的意义。**
**踩坑二：更甚者，CubeMX 每次重新生成代码，都会把我写在 `USER CODE` 区之外的函数冲掉。有一回改了个引脚配置、重新生成，两百多行代码没了，只能从备份里捞回。**
**解决：所有自定义代码皆塞入 `/* USER CODE BEGIN */ ... /* USER CODE END */` 之间，或干脆置于独立的 `.c` 文件里（CubeMX 不会碰这些文件）。同时用 Git 管起来，每完成一项功能便提交一回。**
**收获：工具链的边界须清楚。CubeMX 负"生成骨架"，我负"填血肉"，二者必须物理隔离。这记教训与 10 月 10 号的 bug 同等紧要，只是它折磨的是工程效率，而非功能。**
**问题：机器上曾同时存在两个同名的工程目录，一回"改了 A 目录、烧的却是 B 目录"，困惑了十余分钟。其后将所有工程按日期重命名，只留一个真源。**

## 10月15日：整车联调第一轮

*联调时的整车：X 型麦轮 + 面包板临时电路，这个状态跑了三天*
**今日做了什么：四轮 + 手柄 + 机械臂的 6 路 SG90 舵机，头一回合到一处跑。我分管的，是底盘与手柄这一侧。本周硬件同步完成了三项升级：塑料壳 TT 马达全面换金属壳、底盘底部缠电工胶带防滑防刮、顶部金属盘换塑料板减重。**
**结果：前进后退无碍，左右平移无碍，原地旋转无碍。然撞见两桩新问题：**
**① 联动时速度掉档：手柄控底盘的同时，若另一路信号在驱舵机，主循环周期被拉长，底盘速度便一顿一顿。**
**② 急停响应慢：松开摇杆后，车还要滑行约半米才停。**
**分析：头一问题，是主循环里做了阻塞操作（舵机的 `HAL_Delay`），把控制周期撑大了。做法是把舵机控制移出主循环，改为"设定目标值、由定时器中断去更新"。**
第二问题，"滑行停"本就无制动——这是 10 月 10 号为避刹车停之坑而做的抉择，代价便是停得慢。折中之法：松杆时先给一记短时的反向小占空比（约 100ms、20%），将速度压下，再切回滑行停。
**收获：每一个"修复"都携着代价。刹车停停得住，却与反装轮冲突；滑行停安全，却刹不住。工程上鲜有"纯赚"的方案，只能择那代价可受者。**

## 10月16日：把"能跑"做成"跑得住"

**今日做了什么：今日不写新功能，专攻稳定性。**
列一份清单逐项过：
**① 上电行为：连续上电 20 次，确认不再乱转。这 10 号的修复确然有效。**
**② 断连恢复：中途关掉手柄再开，程序能否自动重连。结果不能，须重新上电。遂加超时判断——连续 200ms 读不到有效包，便重新发初始化序列。**
**③ PWM 限幅：所有速度入口皆加钳位，防参数传错致满速冲出。**
**④ 串口日志：添了个简朴的"状态帧"，每 500ms 打一次四轮速度与手柄状态，便于定位。**
**收获：稳定性并非"没有 bug"，而是在可预期的边界内行为一致。今日所为甚枯，却是"能跑"与"跑得住"之间唯一的路。**
**问题：手柄断连的判断阈值 200ms 是拍的，实测中偶会误判（信号弱时）。眼下先调到 500ms，待更多数据再定。**

## 10月17日：复盘——五个坑、三条原则

**今日做了什么：明日便要整车验收，今日将这段时日踩过的坑尽数理清。**
**五个坑：**
① `#include` 源文件的反模式——图省事，破坏了模块化；
② 两个同名工程目录——"改了 A、烧了 B"，须有唯一真源；
③ CubeMX 覆盖手写代码——生成代码与手写代码必须隔离；
④ DRV8833 的 2 线 / 3 线混淆——二手教程害人，要读原始手册；
⑤ 刹车停 + 反装轮的上电乱转——两个正确的设计撞在一处便是错。
**三条原则：**
**⑥ 逐层排查：从最底层（供电、接线）往上层（协议、逻辑）查，别一上来就疑那最复杂处；**
**⑦ 控制变量：一次只改一件东西，尤其做互换实验时；**
**⑧ 相信数据：灯、声音、丝印皆可能骗人，串口打出的字节不会。**
**想到了：这五条里，有四条并非"不会"，而是"以为会了"。真正绊住我的，从来不是未接触过的知识，是我自以为弄明、实则只记住操作步骤的那截。这也令我后来不大敢说"这个我会了"。**

## 10月18日：验收与下一步

**今日做了什么：整车验收。手柄摇杆驭底盘全向移动，按键控舵机，两路同时作业，连续测了二十多分钟未掉线。**
**结果：功能全部达标。前进、后退、左右平移、原地旋转、加减速、舵机开合，皆跑通。**
**遗留问题（下一步）：**
**① 速度闭环：眼下是纯开环，轮速靠 PWM 估。加编码器后便可做 PID，走直线便不必仰仗拍脑袋的补偿系数。**
**② 摇杆标定自动化：现下手柄参数是写死的，换手柄须重标。可做一个"上电自动标定"流程，令程序自测中心与极限。**
**③ 无线可靠性：目前仍偶发丢包，虽不碍操作，然比赛时若恰在关键动作上掉，代价极大。**
**想到的：自 10 月 1 号点一颗灯，到今日能用手柄开着一台全向车跑，十八天。回头望，最大的斩获不在学会 GPIO、PWM 或 SPI 这些具体 API，而在立起三层认识：能跑（功能实现）、跑对（原理理解）、跑稳（工程约束）。三层之间，各隔一层物事——首层隔的是"动手"，次层隔的是"读文档"，末层隔的是"踩坑"。踩过的坑，终化作判断力。**
