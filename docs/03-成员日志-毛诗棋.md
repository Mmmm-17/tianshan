## 写在前面

这份日志，记的其实是一个人从零起步的十九天。国庆第一天，我连"头文件"意味着什么都讲不明白；而到了 10 月 19 日收尾的此刻，手上这块 STM32F103C8T6 配上一只 PS2 手柄，已能驱动一台四轮麦轮底盘，载着六路 SG90 拼出的机械抓夹，把能量块攥稳了走完整段赛道。中间隔着的，不是灵感，是几百次试错。
每一天都按"做了什么、学了什么、卡在哪、败在哪"四栏去写。我刻意不去粉饰那些真实的笨拙——三遍才跑顺的代码、调错两天的时钟树、被 CubeMX 一键覆盖掉的函数，统统原样留着。文档评估看重的是"为什么这样走"，而非"走成了什么"；把弯路摊开，反而更像一份可信的工程记录。
队长的头衔落到我头上，顺带也把账本塞了进来。于是日志里除了技术，还断续记着每一次队会、每一笔支出的来由。管钱与管技术，在这支队伍里原是一回事：无论代码还是预算，终究都要算清代价。
依赛事手册第 4.3 节对文档的规范，本日志亦作为中期考核仓库的主体内容一并提交。
**关于这个比赛**
CRTC2026 由重庆大学交叉创新中心旗下四支战队联合承办，核心玩法是一场发生在 2400×2400mm 场地内的资源争夺：五分钟之内，尽可能多地收集并携带"能量单元"（白色方块，计 1 分）与"能量核心"（黄色方块，计 4 分）。
机器人的初始包络不得突破 290×195×210mm，展开后亦须收束在 445×400×450mm 以内，整车重量上限 2kg，而供电只允许一枚 7.4V 的 18650 电池组。这几条硬约束，几乎替我们写好了所有机构方案的答案——轻、小、少，是唯一的生路。

## 2026-10-01（周四）

**赛前启动：定分工、定预算、定学习路线**
**今日概况**
**国庆长假头一天，课表空着。我们这支队伍索性约在宿舍楼下的公共空间，把第一次正式会议开了起来。到场的是全队人马：我（电控 + 队长，另外还管钱）、两名机械、一名硬件。这一场谈话，几乎框定了整个国庆的推进节奏；会上我们还敲定了一个名字——天山战队（按手册要求，正式队名写作「天山战队」）。**
**会议内容**
**会议前半段，落在"分工"与"钱"两件事上。说实话，在"队长"这顶帽子扣下来之前，我从没想过财务也会落到自己肩上。报名、采购、报销、记账——条条都要有人盯死，否则临到收尾，报了多少对不上账，报销这一关便卡死。这事，旁人接不了，只能我来。我先在手机上搭了张极简的表，四列：日期、项目、金额、经手人；票据拍完照按日期编号塞进一个相册，纸质的则收进一只信封。规则说穿了也很朴素：谁买谁拍照，当天发群里，我来记——隔上一天再想补，十有八九就漏了。**
分工紧随其后。我把手册第 2.3 节推荐的人员配置先抄上白板：机械 1-2 人、电控/硬件 1-2 人、队长 1 人兼任统筹、操作手兼任。对照着数，我们五个人刚好填满这张表。于是我按「一人主责 + 一人备份」的原则落了子：机械组两人扛建模、3D 打印与整车装配；硬件组一人包走线、供电与焊接；电控这块由我独挑，同时兼着操作手。往后真干起来才看清——机械这边，潘美好始终贴着整机走；另一位则多半守在自己那台电脑前学建模、做了一部分零件，最终没并到整车上。文档方面，我提议各人写各人负责的那块，末了由我来汇总。
**钱，比预想中更难缠。手册白纸黑字：新生组整车造价不推荐超过 400 元，而赛后报销上限，同样卡在 400 元。我先照着官方物资表把每一项价格加了一遍——353.48 元，余量不到 50 块。可这数字，说到底是"刚好凑齐一套"的价；一旦打印件废了、舵机烧了、轮子撞了，窟窿就得自己填。会议给出的结论干脆利落：严格按物资表下单，冗余件控制在 50 元以内，绝不碰任何"看着很强"的贵件。为了让这 50 块长在刀刃上，我们把购物清单按"坏了车就跑不了"和"坏了还能凑合"两档排了序，冗余的钱只留给前一档——末了全压给了 ST-LINK 和一块备用核心板。财务这件事的关键不在省，在可控：花出去多少，我心里得有本账；账清了，后头才敢跟机械组去争那句"这个结构件，能不能不打"。**
后半段，转向国庆期间的学习路线。我主张顺着电控组统一培训的四个板块铺开——GPIO/PWM、电机舵机与 FreeRTOS、SPI 与 PS2 手柄、麦轮运动学解算。这四块，恰好对上中期考核里"电机运动""舵机运动""底盘运动"几项基础指标；学通一块，便能落地一项功能。提议当场通过，并约好：国庆收官前，每人至少把自己那块推进到入门。
**我学到 / 想到的**
① 读手册最有用的一页其实是第 4 页的功能指标表。它把"学会"翻译成了"能演示"，目标一下子清楚了：中期考核 10 月 19 日截止，我们只剩 18 天。
**② 官方物资表里有两处我特意做了笔记：PS2 手柄是可对频锁定的款式，不能用杂牌替代，否则失控后果自负；无线继电器则是通过中期考核后才需要买，现在不着急。**
**问题与卡点**
① 手册里"允许不产出实物演示"也就是说纯靠视频和代码也能交中期考核，但我不想走这条路，太被动。
② 400 元的预算上限意味着几乎没有试错空间，机构方案必须在下单前想清楚，否则一改方案就得贴钱。
明天开始正式的学习和采购。

## 2026-10-02（周五）

**装环境、定采购单**
**今日概况**
今天两件事并行：一是把软件开发环境搭起来，二是把采购单彻底敲定下单。
**软件环境**
上午先装 STM32CubeMX 和 Keil MDK。这一步，比预想中更磨人。CubeMX 前置要装 Java 运行环境；Keil 装罢，还得单独补上 STM32F1 系列的 Device Family Pack。我起初漏了后者，新建工程时死活搜不到 STM32F103C8T6 这个型号，兜兜转转半天才回过味来——是包没装上。随后又把 ST-LINK 驱动一并装好。
**下午仍不死心，把另外两条路也探了探：STM32CubeIDE（ST 家自家的全家桶，CubeMX 和编辑器一体的那种）和 VSCode + 插件（EIDE / Cortex-Debug 那一套）。三套环境各自跑通了一次"点灯级"的空工程，末了拍板：主用 Keil、CubeIDE 当备份、VSCode 专门用来看代码和写笔记。理由很接地气——培训发的例程清一色 Keil 工程格式，跟大部队走最省事；真卡住了，也能让队友直接在我的 Keil 工程上续调，不必来回倒腾格式。**
**试工具链时还顺手养成一个习惯：卡顿超过半小时，就换 AI 问一轮——同一道报错丢给不同模型，给出的切口常常各异：有的直接圈出配置截图的位置，有的先点醒你"先检查时钟树"。AI 不能替我做判断，但能把我的排查范围快速缩小，这半天的性价比，高得有些意外。**
环境装罢，我冲着 CubeMX 的界面发了会儿呆：Pinout、Clock Configuration、Project Manager 三页并排，竟不知该从哪页下手。
**有件事得说透：这套东西我不是"学会"的，是"用起来"的。CubeMX 里每个选项何解，多半是我问出来的——截图糊上去，抛一句"这页我要配什么才能出 PWM"，它便一条条指给我点哪里。我不敢打包票真吃透了背后的原理，但能照着做出、跑通，于这国庆而言，已是最实在的推进。**
**后来给自己攒了套粗线条的记法——Pinout 是"接口"，Clock 是"心跳"，Project Manager 是"出厂设置"；往后几日印证下来，这套理解大体靠谱。**

## 2026-10-03（周六）

**从零补 C 语言**
**今日概况**
国庆第三天，正式开啃语法。我选了 B 站上黑马程序员的 C 语言课程，从第 1 集开始看。坦白说这一天效率不高——看视频的时候觉得都懂，合上就忘了。
**学习过程**
我们大一，编程底子约等于零。第一章讲环境搭建与第一个程序，我照着敲下 `printf("hello")`，竟先报了错——少了个分号；补上再编，又错——头文件忘了包含 `stdio.h`。这两道错报得有点蠢，却是不折不扣的起点，我把它记在笔记头一行。
今天主要啃下三块：
**① 数据类型：`int` 4 字节、`char` 1 字节、`float` 4 字节。脑子里第一次有了概念——单片机上 `int` 的上下限是 ±21 亿；至于 8 位机长什么样，我尚无从想象，只知道手头这块是 32 位。**
**② 变量与作用域：局部变量与全局变量的分野。视频里那句"全局变量在中断里能读到"，当时没绕过来，先原样抄下。**
**③ 循环与判断：`for`、`while`、`if-else`。**
**动手**
我试着在纸上写了一段驱动 LED 闪灯的伪代码思路：
*while (1) {*
*if (count < 5) { LED_ON; count++; }*
*else { LED_OFF; count = 0; }*
*}*
**写完自己揪出一个毛病：这么写其实没有延时，灯会闪得快到肉眼难辨。于是我在纸上自行补了个 `delay()` 的位置。这是我第一次自己发现代码逻辑的问题——虽是最浅的门槛，却也小有成就感。**
**我学到 / 想到的**
① C 语言的坑在于"不报错但结果不对"，比如整型除法 `1/2` 等于 0。这个知识点我专门标了红。
② 视频节奏偏快，1.5 倍速看一遍记不住，我是第一遍 1 倍速看、第二遍 1.5 倍速记笔记。但即使这样，一天下来真正记住的也就数据类型和循环这两块，指针和函数基本是过了一遍眼。
③ 我自己心里清楚：这种学法顶多算"有个印象"，离能写能调还差得远。当时想的是先混个脸熟，等真上手写不出来，再去查、再去问。
**问题与卡点**
① 完全没理解"指针"。视频讲到指针那节我直接跳过了——不是"先放一放"，是看不懂，也就没硬看。
② 没有板子，所有代码都是"纸上验算"，不知道自己写的到底能不能跑。这种不踏实感贯穿了整个国庆。
③ 队长事务：在队群里同步了进度，机械组今天已经在装 Fusion 360 了。
明天继续看语法，重点是函数和结构体。

## 2026-10-04（周日）

**函数、结构体，和第一次"看不懂"**
**今日概况**
继续黑马的 C 语言。今天的主题是函数、数组、结构体、宏定义。
**学习过程**
**函数：形参与实参的差别，我磨了好一阵才略摸着门道——说"想明白"也谈不上，是做着做着才泛起一点手感。我自己的解读是——形参是函数内部的"占位变量"，实参是外面真正递进去的值。视频里拿"复印件"打比方，倒也贴切。**
**结构体：这一节我格外上心，直觉告诉我往后写代码必用得着。视频里定义了个学生结构体，我顺手改成了舵机的版本：**
*typedef struct {*
*int  id;*
*int  angle;*
*int  target;*
*} Servo_t;*
**写罢盯着它看了半晌，忽然咂摸出一层意思：结构体就是把一堆相关的变量打包，让函数可以整包传进去。这与我先前"一个变量只存一个数"的认知全然不同，是一次组织思路上的位移。**
**宏定义：`#define LED_ON 1`。视频里强调要大写，且末尾不加分号。**
**一个失败**
**翻到指针传参那一节，我卡住了。`void f(int *p)` 这样的写法，为何传进去的是地址而非值，函数里又为何要写 `*p = 1`？反复看了三遍，仍攒不出一个能自圆其说的解释。末了我做了个决断：先不硬啃，把它标记成"待解释"，等真正在 STM32 上操作寄存器的时候再回来。**
如今回看，这步棋是对的——脱离具体场景去啃指针，无非死记硬背。
**我学到 / 想到的**
① 写代码之前先想"数据长什么样"，结构体让我第一次有了这种意识。
② 单片机的代码和一个普通 C 程序最大的差别，在于它没有操作系统接管一切，`main` 里通常只有一个死循环。
**问题与卡点**

## 2026-10-05（周一）

**单片机入门：GPIO 和 PWM 是什么**
**今日概况**
**今天起看 keysking 的单片机入门系列。这一套与黑马的气质迥异——黑马讲语言，keysking 讲一块芯片如何被驱动起来。是学长在群里推的，说"新生先看这个，别一上来就啃手册"，果真如此。**
**学习过程**
**第一集讲 GPIO。我头一回弄明白"引脚"究为何物：芯片边缘那些银色的腿，每一根都是一根可被程序拨动的开关。它能被配成输入、输出，或复用功能。有三个词我抄下反复咀嚼：**
**① 推挽输出：能主动输出高、低电平，驱动力强；**
**② 开漏输出：只能拉低，高电平仰仗外部上拉；**
**③ 上拉 / 下拉输入：按键之类要用，否则引脚"悬空"，读出来便是随机值。**
**第二集讲 PWM。这一节我消化得顺：PWM 即一秒内"开"与"关"的比例。占空比 50%，便是一个周期里半数时间高电平。舵机之所以受控，在于它内部认的是高电平持续的时间，一般 0.5ms 到 2.5ms 对应 0° 到 180°。**
我在纸上推了一轮：若 PWM 周期为 20ms（50Hz），则：

| 脉宽 | 对应角度 |
| --- | --- |
| 0.5 ms | 0° |
| 1.5 ms | 90° |
| 2.5 ms | 180° |

**推完这张表，我把"舵机转动"在信号层面串了起来。这是国庆期间最有获得感的一次——纵然只是纸上演算，好歹弄清了 1.5ms 为何是 90°。**
**我学到 / 想到的**
① PWM 的频率和占空比是两码事，舵机看的是"脉宽"，而非占空比本身。这处极易混淆。
② STM32 的定时器可硬件产生 PWM，不必靠程序在循环里手动翻转引脚，这一点比 51 单片机强出不少。
**问题与卡点**
① 视频里提到了 `HAL_GPIO_WritePin()` 这个函数，但我还没在真实代码里用过。
② 手头没有示波器，也没板子，所有关于脉宽的想象都停留在纸面。
③ 截至今天，采购的件到了三样，ST-LINK 和核心板还在路上。
明天看中断和定时器，同时准备把国庆的笔记整理成文档。

## 2026-10-06（周二）

**中断、定时器，环境全部装好**
**今日概况**
上午看完中断与定时器，下午把 CubeMX + Keil 的环境彻底配通，晚上整理笔记。
**中断**
**"中断"这概念，我是头一回撞上，理解走得不顺。视频看完其实只留了个模糊轮廓，真正开窍是后来跟学长聊——他打了个比方：程序正跑在 `main` 里，这时引脚上来了个信号，芯片便立刻暂停手上的活，跳去执行一段特定函数，完了再回来续跑。**
**我把它比作上课：你在做题（main），老师忽然点你（中断），你搁下笔去应答，答完回来接着做；可你做到哪一步，得自己记着——这"记着"，便是中断的现场保护。**
视频里特意点了两条，我记下了：
**① 中断服务函数要短，里头不能写 `HAL_Delay()`，否则整个系统卡死；**
② 共享变量要用 `volatile` 修饰。这关键字在黑马课里我没上过心，今日才懂——它是告诉编译器"这变量可能被别处改，别给我优化掉"。
**定时器**
定时器的本质是个计数器：时钟每来一拍加一，累到设定值便触发一次更新事件。PWM，正是基于这事件去翻转引脚电平。
**此处我撞上个概念坎：预分频（PSC）和自动重装值（ARR）到底谁定频率。我的体会是——PSC 先把时钟"减速"，ARR 决定减完速的时钟要数多少才溢出。故有 频率 = 时钟 / (PSC+1) / (ARR+1)。我把这式子写在笔记本封面，估摸往后得天天见。**
**环境打通**
下午终于把工程从头走了一遍：CubeMX 里选芯片、配时钟树、开一个 GPIO 输出引脚、生成 Keil 工程、编译、0 error。纵然只是一次空编译，整套流程跑通了，心里却踏实不少。
**踩坑记录：CubeMX 的时钟树里，若外部晶振没焊（我们的板子是 C8T6 最小系统板），必须确保 HSE 配对，否则干脆用 HSI，不然生成的初始化代码会卡在时钟启动等待里。这一点，是我们查了才得知的。**
**问题与卡点**
① 中断优先级的概念还很模糊，只知道有 NVIC 这个东西。
② 板子还没到，代码全是"盲写"。
③ 明天是国庆最后一天，得开始把零件凑齐。

## 2026-10-09（周五）

**方案大讨论：从铲子到机械臂**
**今日概况**
**今天没有写一行代码，全队开了一整天会，讨论核心问题：我们的车到底怎么把方块拿起来。会议自清晨拖到正午，下午又单独跟机械组在 Fusion 360 里试原型。这一天，后来成了整个项目里最有价值的一天。**
**为什么这么难**
**先把问题摊开。比赛道具分两种：30mm 的白色"能量单元"（1 分）与黄色"能量核心"（4 分）。黄块的位置又有三处：挂在物资架上（离地 250mm，要够到）、藏在高台下的洞穴里（70×70×50mm 的开口）、搁在中央高地"焦点"上（高 70mm 的平台顶部）。车的初始尺寸不得超 290×195×210mm，展开后最大 445×400×450mm，总重不超过 2kg。**
**难处在于：同一套机构，要能取高处、钻洞穴，还能稳稳搁在自己车上不掉——这几乎是个自相矛盾的命题。**
**方案的迭代**
**机械组在白板上画，我一项项记下。这里我把每个方案"能不能取到"拆成三条判据：够不够得着（高度）、钻不钻得进（洞穴）、掉不掉（携带可靠性）。后头六个方案，便按这三条来裁量：**
**方案一：铲子。 前端一块斜板，贴地推进去把方块铲上来。优点是简单、可靠、成本极低。缺点是只能铲地上的，够不到物资架，也钻不进洞。而我们赛场上大部分黄块都不在地上。**
**方案二：叉车叉子。 像叉车般伸进洞里，靠上下两根叉子把方块夹住。解洞穴问题很在行。但悬空的高处够不着，且方块在叉子上是"放"着的，转弯急些便掉。**
**方案三：钩子。 一只弯钩，勾住方块把它拉过来。适合把物资架上的黄块拽下，但拉下之后方块落了地，还得再捡一回，等于多一道工序。**
**方案四：八爪鱼。 几只爪子自四周合拢，把方块裹住。抓取最稳，几乎不掉落，通用性也最强。可机构太复杂——至少 4 个舵机、繁复的连杆，还得腾出开合的空间，2kg 的重量预算根本撑不住。**
**方案五：机械臂 + 铲子。 机械臂负责够高与钻洞，铲子负责底面承托。设想很美：臂探出去，铲子垫到底下，方块便稳落铲面。问题在两套机构串做一处，重量叠加；且机械臂末端吊着铲子，力臂过长，SG90 根本带不动。**
**方案六：机械抓夹（多 SG90 舵机方案）。 弃掉前置铲刀，改用多个 SG90 舵机组成的机械抓夹：SG90 便宜（几块钱一个）、体积小，可多装几个——根部一个管抬升、中间一个管俯仰、末端两指开合再各一个，整机最多上 6 个 SG90，抓取灵活度远超单一舵机方案。臂可抬到 250mm 够物资架，可放低去钻洞，夹爪夹住方块后靠夹持力保持，不掉。**
**最终决定：方案六**
理由有四条：
**① 一套机构覆盖三种场景，不必在车上装两套，重量最省；**
**② 夹持比承托可靠，一旦违反"携带"的定义便出岔子——手册要求方块在重力下沿任意方向都能随车走，夹住是最稳的；**
**③ SG90 便宜又小，可以堆数量——6 个 SG90 的成本还不及一个 MG995，组合出的自由度却多得多，机构失效时也只需换一只几块钱的舵机；**
**④ 我们距中期考核只剩 10 天，方案越少，零件越容易在期限内做完。**
会议末了定了分工，并约好各自回去写日志、按周对一次进度：机械组当天下午便在 Fusion 360 里试画原型、晚上着手建模；硬件组负责走线与供电，并行研究 DRV8833 和 PS2 接收器；我负责舵机与 PS2 手柄的程序，先把 SG90 转起来。
**我学到 / 想到的**
**这次讨论让我看清一件事：工程上的取舍，不是选"最好的"，而是选"最合适的"。八爪鱼分明最好，却超重、超复杂；机械臂 + 铲子听着最全能，却两套机构彼此拖累。末了回到单个机械臂，反倒是一次"减法"换来的胜局。**
**问题与卡点**
① 机械臂用什么舵机驱动尚未定，SG90 的扭矩断然不够，可 MG995 仍未到货。
② 我这边从明天起正式啃舵机代码，时间只余 10 天。

## 2026-10-10（周六）

**分工落地：第一次接线、第一次烧录**
**今日概况**
今天全队正式分头干活。机械组建模，硬件组拼装，我一个人守着电脑和一块开发板，开始啃舵机。
**团队进度**
**① 机械组：在 Fusion 360 里出了底盘第一版，四轮麦轮布局，中间给电池和驱动板留了槽。今天已经在切片，准备送打印。**

**③ 我：从零开始写第一个工程。**
**接线**
**SG90 三根线我先照着说明书接：棕色 → GND、红色 → 5V、橙色 → 信号。信号线我接在了 PA0，因为 CubeMX 里我看 PA0 对应 TIM2_CH1，正好是一个可以在定时器上输出 PWM 的引脚。**
**这个"引脚和定时器通道对应"的知识点，是今天最大的收获。从前我以为引脚能随便接，今日才晓得能用硬件 PWM 的引脚是有限的，每个引脚背后固定绑定着某个定时器的某个通道。接错了，PWM 便出不来。**
**烧录**
第一次烧录全靠摸索，完整步骤记录如下：

## 2026-10-12（周一）

**突破：舵机转起来了**
**今日概况**
今天只有一个目标：让 SG90 转起来。达成了。
**过程**
**第一步，修时钟树。 在 CubeMX 的 Clock Configuration 页，把 HSE 选成 Crystal/Ceramic Resonator，PLL Source 选 HSE，PLL 倍频设 9，最后 HCLK = 72MHz。生成代码前，我反复确认右上角 SYSCLK 那一栏确实写的是 72。**
**第二步，重新配定时器。 Prescaler 71、Counter Period 19999，这样 72MHz / 72 / 20000 = 50Hz，周期 20ms。计数频率 1MHz，也就是 1 个数对应 1μs——这样 `__HAL_TIM_SET_COMPARE` 写 500 就是 500μs，写 2500 就是 2500μs，直接就是脉宽，不用换算。这个设计，让后续的调试省下不少力气。**
**第三步，烧录。**
*HAL_TIM_PWM_Start(&htim2, TIM_CHANNEL_1);*
*__HAL_TIM_SET_COMPARE(&htim2, TIM_CHANNEL_1, 500);*
*HAL_Delay(1000);*
*__HAL_TIM_SET_COMPARE(&htim2, TIM_CHANNEL_1, 1500);*
**烧进去，按下复位——舵机的摆臂动了一下，然后停住，发出轻微的"吱"声。**
那一刻，我大约愣了两秒。它真的转了。更确切地说，它是按我写下的数字在转——不是巧合，是因果。
**验证**
为确认它确系循脉宽而转，我做了一组对照实验：

| 写入值（μs） | 观察到的情况 |
| --- | --- |
| 500 | 摆臂偏向一侧，约 0° 位置 |
| 1000 | 转动约 45° |
| 1500 | 停在中间，约 90° |
| 2000 | 继续向另一侧，约 135° |
| 2500 | 停在另一侧，约 180° |

五个点全部符合预期。这意味着，脉宽与角度的线性关系确有其事，而非巧合。
**一个值得记的细节**
**中途有一次写 3000，想试试能否越过 180°，结果舵机在尽头"卡卡"地抖，声音很瘆人。我当即断电。后来才明白：超过 2.5ms 的脉宽会驱动机器往物理限位外顶，堵转会烧线圈。幸而只是几秒钟。自那以后，我给代码加上了限幅：**
*if (pulse < 500)  pulse = 500;*
*if (pulse > 2500) pulse = 2500;*
**团队进度**
① 机械组的第一版底盘已装配完成，四个麦轮可自由转向，结构看着相当结实。
② 硬件组敲定了电池座与 DRV8833 驱动板的安放位置。
**③ 我把上午的成果发进群里，机械组当机立断：夹爪的驱动就用 SG90 先做原型，MG995 到货后再换。**
**我学到 / 想到的**
**两天失败，换一次成功。我最大的体会是：调试要有"证明"意识。今天我不只"让它转了"，更做了五个点的对照，证明它确是按我所理解的方式在转。二者云泥之别——前者叫碰巧，后者叫掌握。**

## 2026-10-13（周二）

**啃 PS2 手柄：SPI 是什么**
**今日概况**
舵机通了之后，下一个山头是 PS2 手柄。今天主要在理解 SPI 协议，代码还没写成。
**先搞清楚硬件**
PS2 接收器一共 9 个针脚，包装里附一张模糊不堪的说明图。我对照着针脚，数了半晚才勉强对上：

| 引脚 | 名称 | 接哪里 |
| --- | --- | --- |
| 1 | DATA | MOSI（主机发） |
| 2 | CMD | 空/注意方向 |
| 3 | 9V | 不接 |
| 4 | GND | GND |
| 5 | VDD | 3.3V |
| 6 | CS | 片选，接一个普通 GPIO |
| 7 | CLK | SCK |
| 8 | ATT | 注意 |
| 9 | ACK | 可不接 |

**踩坑：第一版我照"网上的图"接线，把 DATA 与 CMD 接反，读出来的全是 0。后来才发觉，不同来源的图对这两针的定义并不一致——唯以接收器背面丝印为准。**
**SPI 是什么**
**SPI 是同步串行通信：一根时钟线（SCK）、一根数据线、一根片选线（CS）。主机拉低 CS，即宣告"我要与这位从机对话"，随后在时钟的节拍上，一位一位地收发数据。**
**我自己的理解是：它像两个人对着打拍子传纸条，拍子由主机打，从机跟着拍子读/写，片选就是"指名道姓说我在跟谁说话"。**
**PS2 的特别之处在哪儿？它要求拉低 CS 之后，必须按特定的字节序列发问，方才回传数据。典型做法，是先发 `0x01 0x42 0x00 ...`，末了发 0x00 表示开始读取。回包里，第 3、4 字节是按键位图，5~8 字节则是两个摇杆的 X/Y 值——这，便是所谓"模拟模式"。**
**今天做了什么**
① CubeMX 里开 SPI1，模式选 Full-Duplex Master，数据宽度 8 bit，预分频先设大一点保证低速能通；
② 另外配一个 GPIO 输出作为 CS；
③ 写了 `PS2_Init()` 的空框架，里面做的第一件事是给手柄发"进入模拟模式"的指令 `0x01 0x43 0x00 0x01 0x00`。
**代码写至半途，撞上一个要命的问题：手柄需要一个"抖动时钟"来初始化——换言之，正式通信前，CS 得拉高拉低好几回，还要在 SCK 上敲几个脉冲。这处细节，在我读过的资料里仅一笔带过，却恰恰决定了你能否读到数据。**
**我学到 / 想到的**
① SPI 全双工，意即"发出去与收进来同时发生"——每次发一个字节，也必同时收进一个字节。PS2 的读命令，本质上就是"边发边收"。
**② 调试 SPI，最有效的法子从不是盯着代码，而是把收到的原始字节打印出来。今天我在 `while(1)` 里添了一句串口打印，把每次收到的 9 个字节尽数打出，霎时，"到底通没通"便一目了然。**
**问题与卡点**
① 目前串口打印出的全是 `0xFF`，非"未通"即"初始化序列有误"。明日继续。
② MG995 已到货，尚待上机测试。
③ 机械组第二版结构出炉，夹爪亟待我敲定舵机的安装位置与转轴方向——这桩事，我还没给。
明日要双线并进：SPI 通信能否打通，夹爪舵机如何安装。

## 2026-10-14（周三）

**SPI 接通了，但数据是乱的**
**今日概况**
上午把 SPI 通信打通，下午开始处理数据但发现对不上，晚上定位到一个语法层面的问题。
**上午：终于收到数据**
将初始化序列改成下述模样后，打印出的不再是 0xFF：
*PS2_CS_LOW();*
*HAL_SPI_TransmitReceive(&hspi1, cmd, buf, 9, 100);*
*PS2_CS_HIGH();*
`cmd` 是 `{0x01, 0x42, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00}`。
**回传的，是 `0x73 0x5A 0xFF 0x79 0x5A 0x00 0x80 0x80 0x80` 这类字节流。注意第 2 个字节是 0x5A——资料里讲，0x5A 即"手柄已就绪"的标志。一眼望见它，我便知：通了。**
**下午：数据对不上**
然而按键位图与摇杆值都透着古怪。我依资料，将第 4、5 字节拼作一个 16 位无符号数来判别按键：
*uint16_t btn = (buf[3] << 8) | buf[4];*
*if (btn == 0xEF7F) { /* 按下 SELECT */ }*
结果按遍各键皆无反应，`btn` 始终是个固定的怪值。
**晚上：找到问题**
**我将 `btn` 拆作两个字节单独打印，发现 `buf[3]` 恒为 `0xFF`，而 `buf[4]` 却在变。按位拆开看，第 4 字节的低 4 位在动，第 3 字节完全不动。**
**由此我疑心是数据错位。把整段 9 字节全打出来比对，才看清：第 3、4 字节的内容，其实该是"第 4、5 字节"的内容——我读的起始位置错了两位。**
根由在于，我用的命令序列少发了一个字节，致使回包整体前移。资料上的序列是 9 个字节却要发两帧，我第一版只发了单帧。
修正如下：
*uint8_t cmd[9] = {0x01, 0x42, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00};*
*HAL_SPI_TransmitReceive(&hspi1, cmd, buf, 9, 100);*
*// 此时 buf[3] buf[4] 是按键*
*uint16_t btn = ~((buf[3] << 8) | buf[4]);*
**注意这里加了个取反。因为手柄的按键是"低电平有效"——按下为 0，取反之后，按下才变作 1。**
**改毕，按下 SELECT 键，`btn` 化作 `0x0001`。通了！**
**语法上的另一个坑**
中途还撞上一次编译错误，报错 `expression must have pointer-to-struct type`。排查半晌，原来是本该写 `&hspi1`，我却写成了 `hspi1.`——结构体作参数，须传地址。这，恰恰是 10 月 4 号我没啃透的指针问题。
**我回头去看了十分钟指针的视频，这一次，十分钟便懂了。因为这次我有具体的问题要解决，抽象概念终于有了落脚点。**
**团队进度**
① 机械组第二版装配完毕，机械臂底座就位，臂长定为 180mm。
② 我将夹爪舵机的安装方向与转轴位置交付机械组：SG90 竖直安装，转轴朝上，输出轴带动一枚齿轮拨片。
③ 硬件组着手布线。
**我学到 / 想到的**
① "通了"与"用对了"，原是两桩事。今晨我以为通了，实则不过有数据回流；入夜，才真正把协议用对。
**② 指针这桩事再度印证：概念要在用的时候学。**
**问题与卡点**
① 摇杆值尚未换算为 -128~127 的坐标，径直拿去控电机断然不行。

## 2026-10-15（周四）

**把舵机和手柄接起来**
**今日概况**
**今天的目标是让手柄控制舵机。这是整个项目第一次把两块独立做的功能连起来。**
**摇杆值处理**
手柄两支摇杆，每轴在模拟模式下回传 0~255，中间值约 128（实测落在 120~130 之间，且每只手柄略有出入）。我要将其映射成一个堪用的控制量。
**径直取原值，有两个毛病：其一曰死区——手一松，摇杆便抖，128 与 127 来回跳，舵机随之乱颤；其二曰范围——0~255 直接当角度，显然不对。**
我的处置：
*int axis = rx - 128;*
*if (axis > -8 && axis < 8) axis = 0;       // 死区*
*int target = 1500 + axis * 6;              // 128*6 = 768*
*if (target < 500)  target = 500;*
*if (target > 2500) target = 2500;*
*__HAL_TIM_SET_COMPARE(&htim2, TIM_CHANNEL_1, target);*
死区取 ±8，是试出来的：起初取 ±3，抖得厉害；改取 ±20，又嫌迟钝。最终定在 ±8。
**一次失败**
**代码烧入，摇杆推到底，舵机却只动一点点。我算了一笔账：`axis * 6` 至多 768，加在 1500 上得 2268，离 2500 尚差一截。换言之，摇杆推到极限，也够不着 180°。**
**起初我把系数改作 8，情形更糟——舵机在两端疯颤，因为它"够不着"。问题不在系数，在于我的映射是中心对称的，但舵机的实际行程并不关于 1500 对称。**
终改为分段映射：
*if (axis >= 0) target = 1500 + axis * 7;   // 向右最多 +890*
*else           target = 1500 + axis * 9;   // 向左最多 -1152*
**为何两边不对称？因为我实测了这台 SG90：脉宽 500 时角度不到 0°，2500 时已越过 180°，它的机械零位偏了些。所以代码必须按实测来，不能按说明书。**
**迟滞保护**
**摇杆推回中位，舵机仍会微微发抖。我添了一道迟滞：唯当目标值与当前值之差超过 10μs，方才更新。**
*if (abs(target - current) > 10) {*
*__HAL_TIM_SET_COMPARE(&htim2, TIM_CHANNEL_1, target);*
*current = target;*
*}*
加上这一道，抖动遂消。
**团队进度**
① 机械臂装配完工，SG90 以热熔胶临时固定在夹爪上，能开合了，只是夹合力偏小——夹住方块后轻轻一碰便掉。
② 硬件组将四路电机驱动接线完毕，尚未上电测试。
③ 我这一侧的电控方案已可演示：一只舵机，被手柄实时操控。
**我学到 / 想到的**
**① 死区和迟滞是两个不同的东西。死区是"小信号当没信号"，迟滞是"变化不大就不动"——前者防抖，后者止住反复触发。**
② 实测胜于手册。舵机的输出电压、脉宽、行程，几乎每台个体迥异，尤以几块钱的 SG90 为甚。
**问题与卡点**

## 2026-10-16（周五）

**集成：一屏代码管住三个舵机和一个手柄**
**今日概况**
今天是全队最忙的一天。机械、硬件、电控三条线同时收口，我第一次把"手柄读数据 + 三路舵机 + 四路电机"放进同一个工程。
**换 MG995**
夹爪上的 SG90，换作 MG995。反差立现：
① 同样 1500 的脉宽，MG995 抵中位更快，声更沉；
② 徒手去掰，几乎纹丝不动；SG90 稍加力便被掰开；
**③ 夹住一个 11 克左右的方块，用力甩手臂，方块没掉。**
这一下，"方块携带"的核心可行性被彻底打通。代价是重量——MG995 较 SG90 重了近 30 克，整车重量须重新过秤。
**定时器分配**
三路舵机若全走软件 PWM，必互相打架，只能悉数迁入硬件通道。我查了 F103C8T6 的定时器资源，最终如此分配：

| 通道 | 引脚 | 用途 |
| --- | --- | --- |
| TIM2_CH1 | PA0 | 机械臂根部旋转 |
| TIM2_CH2 | PA1 | 机械臂抬升 |
| TIM2_CH3 | PA2 | 夹爪开合 |

**同一定时器的三通道共用 PSC 与 ARR，恰合舵机"统一 50Hz"之需，反倒省心——配一次参数，三路都能用。**
**代码结构**
工程之内，我做了轻量分层：
*main.c*
*├─ Servo_SetAngle(ch, pulse)   // 单路设置，内部做限幅*
*├─ PS2_Read(buf)               // 读 9 字节*
*├─ PS2_Parse(buf, &state)      // 解析成按键 + 摇杆*
*└─ while(1) { 读手柄 → 映射 → 写舵机 }*
`PS2_Parse` 中，我把 12 个按键定义成位掩码，以单个 `uint16_t` 表达，按键判定便是 `state.buttons & PS2_UP`。这般写法，是我从结构体的思路上自行演化而来，写来颇觉顺手。
**一个真实事故**
**正午调试，我改了 `main.c` 里的一行，Keil 点编译，显示 `0 Error`，烧录——程序却全无反应。折腾整一个钟头，终获真相：CubeMX 生成代码时，我的自定义代码写在了 `/* USER CODE BEGIN */` 与 `/* USER CODE END */` 之外，重新生成时被覆盖。**
**这是我头一回真正读懂那几行注释的意味——它们是 CubeMX 的"保护带"，写于其中的代码方不被覆盖。 自那以后，我的全部逻辑都栖身 USER CODE 区，或干脆另开 `.c/.h` 文件。**
**成果**
入夜八点，首度完整演示：
① 左摇杆掌管机械臂底座旋转与抬升；
② 右侧四个按键操控夹爪开合；
③ 三路舵机齐动，互不干扰；
④ 手柄断开后再连，仍能续上。
**问题与卡点**
① 四路电机尚待验证，麦轮底盘眼下仅"能推着走"。
② 整车重量未称，2kg 乃硬线。
③ 19 号中期考核，仅余 3 天；功能演示视频与文档仓库，皆未动手。
**明天计划**
全力冲刺电机与底盘，入夜写文档、录视频。

## 2026-10-18（周日）

**硬件升级与 6 路舵机扩展**
**今日概况**
**今日是"升级日"。核心任务三桩：换金属 TT 马达、改底盘、夹爪扩到 6 路 SG90。三事上午定案，下午动手，晚间验证。**
**金属 TT 马达替换塑料壳马达**
**这几日最直观的感受是：塑料壳的 TT 马达太"软"了。昨日试车，推一下车壳，便闻马达内齿轮打滑的"咔"声，输出轴徒手即可捏停。查参方知：塑料壳版齿轮组间隙偏大、壳体刚性差，扭矩衰减显著。**
**换上金属壳 TT 马达（同样是 1:90 减速比）后，反差立现：壳体不再有弹性形变，齿轮间隙明显收窄，空载噪声反比塑料壳更沉。更关键在堵转特性——塑料壳堵转是"壳体在振"，金属壳堵转是"整个车身在推"，力道全然不在一个量级。四轮尽数换装，余下塑料壳马达留作备件。**
**底盘缠电工胶带、顶板换塑料**
两处改动，皆被重量所逼：
**① 底盘缠电工胶带：底盘金属板裸奔了两日，试车时底部刮出数道痕，且金属面太滑，置于坡道便往下溜。全队商议，决计将底部整层缠上电工胶带——防滑、防刮、绝缘三合一，成本几可不计。缠时须顺同一方向压边，否则跑几趟便翘起。**
**② 顶部盘金属换塑料：顶部那块金属盘，本为压住电池与舵机线而生，称重后才发觉它是全车最"冤"的份量——担的是固定之责，耗的却是与电池相仿的克重。换作一块 2mm 塑料板，减重 40 多克，刚性够用。2kg 的总重上限是硬线，能省的每一克都得省。**
**6 路 SG90 的硬件通道扩展**
夹爪机构由演示级的 3 路，升级至参赛级的 6 路：根部旋转、抬升各占一路，俯仰一路，末端两指开合各一路，再加一路腕部微调。TIM2 仅 3 通道，不够。
**解法查自 F103C8T6 的引脚复用表：TIM2 的 CH1~CH3 加 TIM3 的 CH1~CH3，一共 6 个硬件 PWM 通道，恰好覆盖。两定时器分置 50Hz、脉宽 500~2500μs，共用同一套 `Servo_SetPulse()` 接口，唯所传定时器句柄不同。**
**踩坑：TIM3 与 TIM2 的时钟源并不同（TIM3 亦在 APB1 上、同为 72MHz，但预分频须单独配），起初照抄 TIM2 参数，竟忘了 TIM3 的 PSC，致两路舵机转速明显参差。对着手册重算一遍 APB1 时钟，方改对。**
**一次小失败**
**午后试 6 路同时动作，板子又复位一回——与 16 号那次同属电压跌落，然此番 470μF 电容已不够看。6 个 SG90 同时堵转的瞬时电流，较 3 路时翻了一倍。加第二枚电容、并将舵机供电与主控供电分线走之后，复位消失。**
**明天计划**
中期考核最后一日：录视频、填文档仓库、查规则测评。所有材料，24:00 前必交。
